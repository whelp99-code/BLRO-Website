## 한눈에 보기

GKE 릴리스 노트 September 01, 2026 항목은 버전 1.35.1-gke.1031000 이상에서 Service용 자동 방화벽 여러 개의 우선순위를 1000에서 999로 바꾸고, 다른 자동 규칙이 명시적으로 허용하지 않은 트래픽을 거부하는 규칙을 만든다고 적습니다.

- 결정: 그 버전으로 올리기 전에 우선순위 1000인 맞춤 allow·deny를 숫자상 더 낮은 값(999 이하)으로 내릴지
- 전제: VPC 방화벽은 숫자가 작을수록 우선한다. 릴리스 노트는 맞춤 규칙이 1000이면 예기치 않은 동작이 날 수 있다고 적는다
- 문서 차이: 개념 문서는 k8s-fw 패밀리를 1.35.1-gke.1473000, k8s2 패밀리를 1.35.1-gke.1031000으로 적는다
- 범위: 사용자 관리 방화벽으로 자동 생성을 끄는 결정과 섞지 않는다. Service 자동 규칙 우선순위와 deny 규칙만 가른다

## 문제 상황

맞춤 VPC 규칙으로 GKE Service 방화벽을 덮어쓰던 클러스터가 1.35.1-gke.1031000 이상으로 올라가면, 자동 allow가 999로 내려가고 새 deny가 생깁니다. 맞춤 규칙이 그대로 1000이면 더 이상 자동 규칙보다 앞서지 못합니다.

릴리스 노트는 업그레이드 전에 우선순위 1000인 맞춤 allow·deny를 999 이하로 바꾸고, 새 자동 deny가 외부 IP를 쓰는 로드 밸런서에 필요한 트래픽을 막지 않는지 확인하라고 적습니다.

개념 문서 Automatically created firewall rules는 달리 적지 않으면 자동 규칙 우선순위가 1000이라고 적습니다. GKE Service firewall rules 절은 이름을 나눕니다. k8s-fw-[loadbalancer-hash] allow와 그 deny, 일부 헬스 체크 규칙은 1.35.1-gke.1473000부터 allow 999·deny 1000입니다. k8s2-[cluster-id]-… allow와 deny, 일부 헬스 체크 규칙은 1.35.1-gke.1031000부터 allow 999·deny 1000입니다. 릴리스 노트의 1.35.1-gke.1031000과 개념 문서의 1.35.1-gke.1473000을 한 버전으로 합치지 않습니다.

사용자 관리 방화벽 문서는 자동 생성을 끄려면 클러스터에 --disable-l4-lb-firewall-reconciliation을 준다고 적습니다. 전제는 1.31.3-gke.105600 이상입니다. 이 플래그는 노드 간 통신이나 헬스 체크용 자동 규칙에는 영향을 주지 않습니다. 자동 생성을 끄는 일과 우선순위만 내리는 일을 한 변경으로 보지 않습니다.

## 지금 결정할 것

- 클러스터를 1.35.1-gke.1031000 이상으로 올리기 전에 맞춤 규칙 우선순위를 999 이하로 내릴지
- 대상 Service가 k8s-fw 패밀리인지 k8s2 패밀리인지, 기준 버전을 어느 줄로 볼지
- 새 자동 deny가 외부 IP 로드 밸런서 필수 트래픽을 막는지 점검할지
- 자동 생성을 유지한 채 우선순위만 맞출지, --disable-l4-lb-firewall-reconciliation으로 사용자 관리로 갈지
- 사용자 관리는 subsetting 내부 LB와 백엔드 서비스 기반 외부 LB에만 적용된다는 한계를 수용할지

## 의사결정 기준

### 릴리스 노트 버전과 규칙 패밀리 버전을 한 줄로 쓰지 않습니다

릴리스 노트 변경의 기준은 1.35.1-gke.1031000입니다. 개념 문서는 k8s-fw 패밀리에 1.35.1-gke.1473000을 적습니다. 업그레이드 체크리스트에 클러스터 버전과 실제 규칙 이름 접두사를 같이 적습니다.

### 맞춤 규칙 1000과 자동 규칙 999를 같은 우선순위로 보지 않습니다

숫자가 작을수록 먼저 적용됩니다. 맞춤 규칙이 자동 allow를 이기려면 자동 규칙보다 숫자가 작아야 합니다. 자동 allow가 999가 된 뒤에도 맞춤이 1000이면 덮어쓰지 못합니다.

### 새 자동 deny와 필수 로드 밸런서 트래픽을 확인합니다

릴리스 노트는 새 deny가 외부 IP를 쓰는 로드 밸런서에 필요한 트래픽을 막지 않는지 보라고 적습니다. allow만 보고 deny 생성을 건너뛰지 않습니다. gcloud compute firewall-rules list --filter="name~k8s" 또는 콘솔 VPC network의 Firewall에서 이름과 우선순위를 봅니다.

### 사용자 관리 끄기와 우선순위 조정을 섞지 않습니다

사용자 관리 문서는 자동 생성을 끌 수 있는 Service 유형과 끌 수 없는 유형을 나눕니다. 내부 LB이면서 subsetting이 없거나 타깃 풀 기반 외부 LB는 자동 생성을 끌 수 없습니다. 우선순위만 맞추는 경로와 자동 생성을 끄는 경로를 따로 승인합니다.

## 실무 체크리스트

1. 업그레이드 대상 클러스터 버전이 1.35.1-gke.1031000 이상인지 기록합니다.
2. 맞춤 VPC 규칙 중 Service를 덮는 규칙의 우선순위가 1000인지 목록화합니다.
3. 덮어쓸 맞춤 규칙을 999 이하로 내릴지 정합니다.
4. 실제 규칙 이름이 k8s-fw-인지 k8s2-인지 구분해 개념 문서 버전을 대조합니다.
5. 업그레이드 후 자동 allow가 999인지, 대응 deny가 생겼는지 확인합니다.
6. 외부 IP 로드 밸런서에 필요한 트래픽이 새 deny에 걸리지 않는지 점검합니다.
7. 자동 생성을 끄려면 --disable-l4-lb-firewall-reconciliation 대상이 subsetting 내부 LB 또는 백엔드 서비스 기반 외부 LB인지 확인합니다.
8. 「이번 주 운영 확인」 PASS = gcloud compute firewall-rules list --filter="name~k8s" 또는 콘솔 VPC network → Firewall에서 자동 Service allow가 문서 값(999)이고, 이겨야 하는 맞춤 규칙은 그보다 숫자가 작다. FAIL = 클러스터가 1.35.1-gke.1031000 이상인데 맞춤 allow·deny가 여전히 1000이고 자동 규칙은 999이다.

- 방화벽 제품, CNI, 보안 장비의 우열이나 가격 비교
- ClusterNetworkPolicy Admin·Baseline 글을 다시 쓰는 범위
- GKE가 만든 규칙을 수동으로 고치거나 지워도 된다는 가정. 개념 문서는 되돌림과 예기치 않은 동작을 경고한다
- 우선순위만 바꾸면 모든 로드 밸런서 트래픽이 보장된다는 주장
- 인프라 컨설팅 베이스라인 재작성
