가상화 마이그레이션은 VM을 새 플랫폼에서 켜는 작업이 아닙니다. **업무 중단 허용 범위, 의존성, 데이터 보호, 네트워크 경로, 운영 책임을 같은 전환 계획으로 묶는 일**입니다. 이 조건이 빠지면 일정은 있어도 전환 판단은 남지 않습니다.

## 이전 전에 합의할 7가지

| 조건 | 질문 | 확인 결과 |
| --- | --- | --- |
| 업무 우선순위 | 어느 서비스가 먼저 복구돼야 하는가 | 업무별 최소 기능과 승인자 |
| 의존성 | DB·인증·파일·외부 연동은 무엇인가 | 전환 단위와 순서 |
| 변경 창 | 언제 멈추고, 언제 복귀할 수 있는가 | 업무 소유자 승인 일정 |
| 데이터 보호 | 백업과 복구는 실제로 검증됐는가 | 복구 리허설 기록 |
| 네트워크 | IP·DNS·방화벽·연결 경로는 어떻게 바뀌는가 | 전환 전후 흐름표 |
| 운영 도구 | 모니터링·패치·알림은 누가 수행하는가 | 운영 인수 체크리스트 |
| 롤백 | 어떤 조건에서, 누가, 어디로 복귀시키는가 | 중단 기준과 책임자 |

## 전환 파동을 설계하는 방법

1. 첫 파동에는 의존성이 낮고 복구가 쉬운 대표 업무를 넣습니다. 가장 쉬운 VM이 아니라 **절차를 검증할 수 있는 업무**여야 합니다.
2. PoC에서 기능, 네트워크, 백업·복구, 모니터링, 운영자 실행을 한 시나리오로 확인합니다.
3. 두 번째 파동부터는 전 단계에서 확인된 소요시간·오류·용량 가정을 반영합니다.
4. 중요 업무는 업무 소유자 승인, 리허설, 전환 창, 롤백 기준을 모두 갖춘 뒤 진행합니다.

## 무엇을 완료로 볼 것인가

완료 조건은 “VM이 부팅됨”이 아닙니다. 업무 사용자가 최소 기능을 확인하고, 운영팀이 모니터링·백업·복구·장애 대응을 수행하며, 책임자와 문서가 인수된 상태여야 합니다. VMware의 공식 마이그레이션 자료도 애플리케이션 의존성 파악과 롤백의 복잡성을 전환 초기 고려사항으로 다룹니다. [VMware HCX migration overview](https://www.vmware.com/docs/vmw-hcx-for-application-migration-solution-overview)

## 흔한 오류와 보류 기준

단일 VM 기준으로만 일정을 짜면 애플리케이션 연결과 복구 순서를 놓칩니다. 또 성능 측정 없이 목표 용량을 확정하면 다음 파동에서 가정이 무너집니다. 의존성, 변경 창 또는 복구 기준 중 하나라도 비어 있으면 해당 업무는 전환 대상이 아니라 **진단 보류 대상**으로 남겨야 합니다.

## 이 글을 읽은 뒤 남겨야 할 것

워크로드별 전환 파동표, 의존성 지도, PoC 통과 기준, 롤백 실행표가 남아야 합니다. 이 결과물은 특정 제품의 우위 판단이 아니라 유지·전환·혼합 운영을 비교하는 공통 기준입니다.
