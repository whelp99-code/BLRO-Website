## 한눈에 보기

Assistants API 개념 문서와 클래식 포털 이전 안내는 Assistants API가 종료됐고, 워크로드를 일반 공급 Microsoft Foundry Agents service로 옮기라고 적습니다. 확인일 2026-08-31 기준으로 안내된 종료일 2026-08-26은 이미 지났습니다.

영향 범위는 /assistants, threads, runs를 쓰는 워크로드와, Responses API가 없는 리전에 둔 Foundry resource입니다. 전제는 마이그레이션 도구가 에이전트 정의와 코드 구성은 옮기지만 과거 runs, threads, messages 상태 데이터는 옮기지 않는다는 점입니다. 검증 항목은 create_agent를 create_version으로 바꿨는지, conversation과 response 출력이 나오는지, 리전이 Responses API와 Foundry Agent Service를 지원하는지, Azure Functions tool 대체안을 옮기기 전에 정했는지입니다.

- 결정: /assistants 경로를 Foundry Agent Service와 Responses API로 옮길지, 리전을 먼저 바꿀지
- 전제: 2026-08-26에 Assistants API가 sunset되고 azure-ai-inference도 같은 날 종료된다
- 도구: Azure Functions tool은 클래식에서 Yes(GA)이고 신규 Foundry Agent Service에서는 No다
- 범위: 에이전트 게시 신원 글의 재작성이 아니다. 호출 주체는 그 글의 범위다

## 문제 상황

클래식 Assistants API로 만든 워크로드를 그대로 두면, 종료된 API와 새 포털의 리전 제약이 한 변경에 섞입니다.

Assistants API 개념 문서는 Assistants API가 retired이며 일반 공급 Microsoft Foundry Agents service를 쓰라고 적습니다. 마이그레이션 가이드로 워크로드를 업데이트하라고 적습니다.

클래식 포털 이전 안내는 핵심 날짜를 2026-08-26 두 건으로 둡니다. azure-ai-inference 패키지가 종료되고 openai 패키지로 옮기라고 적습니다. 같은 날 Assistants API가 sunset되고 일반 공급 Microsoft Foundry Agents service를 쓰라고 적습니다. 에이전트를 Assistants API에서 Responses API로 다시 쓰라고 적습니다.

같은 안내는 Responses API와 Foundry Agent Service가 모든 Azure 리전에 있지 않다고 적습니다. Foundry resource가 미지원 리전에 있으면 현재 포털에서 에이전트를 만들거나 실행할 수 없고, 에이전트와 다른 Responses API 기능이 동작하지 않는다고 적습니다. 포털에 에이전트가 안 뜨는 증상을 코드 오류만으로 보지 말고 리전 지원을 먼저 대조합니다.

마이그레이션 가이드는 마이그레이션 도구가 GitHub에 있다고 적습니다. 도구는 에이전트 정의, thread 생성, message 생성, run 생성 같은 코드 구성을 옮깁니다. 과거 runs, threads, messages 같은 상태 데이터는 옮기지 않습니다. 옮긴 뒤 새 코드를 실행하면 새 형식의 상태 데이터가 생긴다고 적습니다. 과거 대화 이력이 자동으로 넘어왔다고 보고하지 않습니다.

도구 표는 Azure Functions tool을 클래식에서 Yes(GA), 신규에서 No로 적습니다. Function tool은 양쪽 모두 Yes(GA)입니다. Azure Functions tool을 쓰는 워크로드는 대체안을 정하기 전에 마이그레이션을 승인하지 않습니다.

## 지금 결정할 것

- /assistants, threads, runs 호출을 이번 창에서 멈출지
- create_agent를 create_version으로 바꿀지, PromptAgentDefinition을 둘지
- threads와 runs를 conversation과 response 출력으로 바꿀지
- Foundry resource 리전이 Responses API와 Foundry Agent Service를 지원하는지
- 미지원 리전이면 지원 리전에 새 Foundry resource를 만들지
- Azure Functions tool을 어떤 대체 도구로 둘지
- 마이그레이션 도구가 옮기지 않는 과거 상태 데이터를 어떻게 남길지

## 의사결정 기준

### 종료된 Assistants API와 새 Agents를 같은 런타임으로 보지 않습니다

개념 문서는 Assistants API가 retired라고 적습니다. 이전 안내는 2026-08-26 sunset을 적습니다. 확인일 기준으로 그 날짜는 지났습니다. /assistants 경로를 운영 기본값으로 두지 않습니다.

### 리전 지원을 포털 표시보다 먼저 봅니다

이전 안내는 Responses API와 Foundry Agent Service가 모든 리전에 있지 않다고 적습니다. 미지원 리전의 Foundry resource에서는 현재 포털에서 에이전트가 동작하지 않습니다. 코드를 고쳤는데 에이전트가 안 뜨면 리전 목록을 먼저 대조합니다.

### create_agent와 create_version을 같은 호출로 보지 않습니다

마이그레이션 가이드는 이전 SDK의 create_agent를 create_version으로 바꾸라고 적습니다. 새 메서드는 kind, model, instructions가 있는 구조화 정의를 씁니다. create_agent가 제거된 SDK에서 예전 호출을 남기지 않습니다.

### conversation과 response 출력을 thread와 run과 같은 상태로 보지 않습니다

이전 안내는 Threads가 Conversations로, Runs가 Responses로 바뀐다고 적습니다. 마이그레이션 가이드도 threads를 conversations로, runs를 responses로 바꾸라고 적습니다. 도구가 과거 상태를 옮기지 않으므로, 이전 thread 이력이 새 conversation에 있다고 가정하지 않습니다.

### Azure Functions tool은 옮기기 전에 대체합니다

도구 표는 Azure Functions tool이 신규 Foundry Agent Service에 없다고 적습니다. 클래식 Yes(GA)를 신규에서도 된다고 보지 않습니다. 대체 도구를 정한 뒤에만 마이그레이션을 승인합니다.

## 실무 체크리스트

1. /assistants, threads, runs를 호출하는 워크로드와 배포 리전을 목록으로 남깁니다.
2. Foundry resource 리전이 Responses API와 Foundry Agent Service를 지원하는지 이전 안내의 리전 목록과 대조합니다. 미지원이면 지원 리전에 새 자원을 둘지 적습니다.
3. create_agent 호출을 create_version과 PromptAgentDefinition으로 바꿨는지 확인합니다.
4. thread 생성과 run 폴링을 conversation과 response 출력으로 바꿨는지 확인합니다.
5. Azure Functions tool 사용처를 찾고, 신규에서 No인 상태를 반영한 대체안을 적습니다.
6. 마이그레이션 도구를 쓰면 코드 구성만 옮기고 과거 runs, threads, messages는 남기지 않는다는 점을 변경 요청에 적습니다.
7. azure-ai-inference를 openai 패키지로 바꿨는지, 종료일 2026-08-26을 같은 기록에 남기는지 확인합니다.
8. 옮긴 뒤 에이전트 생성, conversation 생성, response 출력, 도구 호출 실패를 시나리오로 확인합니다.
