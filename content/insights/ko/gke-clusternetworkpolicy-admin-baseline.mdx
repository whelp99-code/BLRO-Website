## 한눈에 보기

2026-08-10 Google Cloud 블로그는 GKE에 ClusterNetworkPolicy를 도입했다고 적습니다. 클러스터 전역 Admin·Baseline 가드레일과 네임스페이스 NetworkPolicy를 계층으로 나눕니다.

- 결정: 플랫폼 Admin 정책과 개발자 네임스페이스 정책을 같은 권한으로 둘지, RBAC와 tier로 가를지
- 전제: how-to는 GKE 1.36.0-gke.4447000 이상과 Dataplane V2를 요구한다
- 평가 순서: Admin 먼저, 그다음 표준 NetworkPolicy, 마지막 Baseline, 미매칭 시 암묵적 allow
- 범위: 서비스 메시나 FQDN 정책 전체가 아니라 클러스터 전역 CNP Admin·Baseline 경계

## 문제 상황

표준 NetworkPolicy는 네임스페이스 범위입니다. 블로그는 관리자가 이를 전역 가드레일로 쓰면 충돌과 운영 부담이 생긴다고 적습니다. ClusterNetworkPolicy는 SIG-Policy의 오픈소스 표준으로, Admin·NetworkPolicy·Baseline 세 층을 위에서 아래로 평가합니다.

Admin은 최상위입니다. Accept나 Deny가 맞으면 평가가 끝납니다. Pass는 아래 층에 결정을 넘깁니다. Baseline은 가장 낮고, 네임스페이스 정책으로 덮어쓸 수 있는 기본 자세를 둡니다. 개념 문서는 어떤 층에도 안 맞으면 GKE 기본이 암묵적 allow라고 적습니다.

how-to는 API가 policy.networking.k8s.io/v1alpha2이고 프리뷰·알파라고 적습니다. CRD가 바뀔 수 있다고 경고합니다. 블로그는 1.36 이상 프리뷰라고 적고, how-to는 1.36.0-gke.4447000 이상, 개념 문서는 1.36.1-gke.1067000 이상을 적습니다. 운영 승인에는 실제 클러스터 마이너·gke 패치와 Dataplane V2 여부를 같이 적습니다.

## 지금 결정할 것

- 클러스터가 Dataplane V2이고 문서가 적은 버전 이상인지
- Admin deny·allow를 누가 쓰는지, Baseline deny-by-default를 누가 쓰는지
- Pass로 네임스페이스에 위임할 트래픽과 Admin에서 끝낼 트래픽을 나눌지
- kube-dns 등 핵심 서비스 allow를 Admin에 둘지
- CiliumClusterwideNetworkPolicy 기존 규칙을 CNP로 옮길지

## 의사결정 기준

### Admin과 Baseline을 같은 정책으로 쓰지 않습니다

블로그와 개념 문서는 Admin을 필수 가드레일, Baseline을 개발자가 덮을 수 있는 기본값으로 나눕니다. 민감 네임스페이스 격리는 Admin Deny로 두고, 클러스터 기본 deny-all은 Baseline에 둡니다. 한 CNP에 둘을 섞어 승인하지 않습니다.

### Pass와 Accept·Deny를 구분합니다

how-to는 Deny와 Accept가 파이프라인을 즉시 끊고, Pass만 다음 tier로 넘긴다고 적습니다. 공유 플랫폼 서비스는 Accept, 민감 vault는 Deny, 그 외 마이크로서비스는 Pass 후 네임스페이스 NetworkPolicy로 허용하는 패턴을 블로그 예시가 보여 줍니다. Pass 없이 Admin Accept만 늘리면 개발자 정책이 사실상 무시됩니다.

### 버전·Dataplane V2 전제를 숨기지 않습니다

how-to Before you begin은 1.36.0-gke.4447000 이상과 Dataplane V2를 요구합니다. 개념 문서는 1.36.1-gke.1067000 이상을 적습니다. 블로그는 1.36 이상 프리뷰라고만 적습니다. kubectl get clusternetworkpolicies 전에 클러스터 버전과 Dataplane V2를 확인합니다.

### 신규 전역 정책은 CNP를 우선합니다

개념 문서는 신규 배포에 독점 CiliumClusterwideNetworkPolicy보다 Kubernetes-native ClusterNetworkPolicy를 쓰라고 적습니다. 기존 Cilium 전역 규칙이 있으면 이전 일정과 병행 기간을 승인 조건으로 남깁니다.

## 실무 체크리스트

1. 클러스터 버전이 1.36.0-gke.4447000 이상인지 확인합니다.
2. Dataplane V2 사용 여부를 확인합니다.
3. kubectl get clusternetworkpolicies로 기존 CNP 유무를 봅니다.
4. Admin 정책 작성·적용 RBAC와 Baseline 작성 주체를 나눕니다.
5. kube-dns 등 필수 Allow를 Admin에 둘지 정합니다.
6. 민감 네임스페이스 Deny를 Admin에 둘지 정합니다.
7. Baseline deny와 네임스페이스 override 시험 시나리오를 적습니다.
8. 주간 점검: kubectl get clusternetworkpolicies와 버전·Dataplane V2를 함께 확인합니다.
