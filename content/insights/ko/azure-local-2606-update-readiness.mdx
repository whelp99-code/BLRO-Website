## 핵심 주장

Azure Local 2606 변경 창은 목표 버전 표시가 아니라 지원 경로, OEM 콘텐츠, 상태 검사와 실패 중단 조건이 기록된 경우에만 검토합니다.

근거와 결정: Microsoft의 릴리스·업데이트 단계·알려진 문제 문서를 기준으로 노드별 현재·목표 상태와 준비 결과를 설치 승인 근거로 사용합니다.

## 주장과 근거

| 주장 또는 결정 | 근거 | 운영 조치 |
| --- | --- | --- |
| 업데이트 경로를 노드별 solution version과 OS build로 확인한다 | Microsoft Azure Local 릴리스 정보 | 현재·목표 버전과 OEM 상태를 표로 기록 |
| 준비 단계 실패는 설치 전에 처리한다 | Microsoft Azure Local 업데이트 단계 문서 | Critical·Warning 결과와 예외 승인 기준을 기록 |

## 한눈에 보기

- 대상: Azure Local 하이퍼컨버지드 배포의 2606 업데이트를 검토하는 운영팀
- 핵심 결정: 현재 solution·OS build, 지원되는 업데이트 경로, OEM 콘텐츠, 상태 검사, 실패 시 중단 기준
- 운영 원칙: 업데이트 가능 표시와 설치 준비 완료를 같은 상태로 보지 않음
- 주의 조건: 알려진 문제와 보안 정책 충돌을 변경 창 전에 확인하고, 실패한 업데이트를 원인 확인 없이 반복하지 않음

## 문제 상황

Azure Local 2606은 solution version 12.2606.1003.205와 OS build 26100.32995를 사용합니다. 그러나 목표 버전만 확인해서는 실제 변경 창을 승인하기 어렵습니다. 현재 release train과 누적 업데이트 경로, 하드웨어 공급자 콘텐츠, 클러스터 상태 검사, 알려진 문제, 워크로드 여유 용량이 함께 맞아야 합니다.

Microsoft의 업데이트 흐름은 준비와 설치로 나뉩니다. 준비 단계에서 패키지 검증과 상태 검사를 통과하지 못하면 설치를 시작하기 전에 원인을 제거해야 합니다. 따라서 “업데이트가 보인다”보다 “준비 결과와 복구 조건이 기록돼 있다”를 승인 기준으로 삼는 편이 안전합니다.

## 지금 결정할 것

- 목표 경로: 현재 solution·OS build에서 지원되는 다음 경로인지 확인하고 노드별 현재·목표 버전표를 만듭니다.
- 사전 콘텐츠: AdditionalContentRequired 또는 OEM SBE 콘텐츠 필요 여부와 확보 상태를 기록합니다.
- 설치 승인: Critical·Warning 상태 검사 결과의 실패·예외·승인 기준을 정합니다.
- 변경 창: 워크로드 이동 여유와 운영 영향을 바탕으로 용량·세션·중단 계획을 만듭니다.
- 실패 대응: 중단 단계, 로그 수집, 지원 전환, 재시도 금지 조건과 복구 담당자를 정합니다.

## 의사결정 기준

### 버전 번호가 아니라 업데이트 경로를 확인합니다

Azure Local은 여러 release train과 OS build를 함께 운영합니다. 각 릴리스의 지원 기간과 선행 누적 업데이트 조건이 있으므로 포털에 표시된 목표 버전만 보고 건너뛰기 경로를 가정하지 않습니다. 노드별 solution version, OS build, OEM 패키지 상태를 한 표에 모읍니다.

### 준비 단계 결과를 변경 승인 근거로 씁니다

준비 단계는 콘텐츠 다운로드·검증·압축 해제와 상태 검사를 수행합니다. Critical 결과는 설치를 차단하고, Warning도 기본적으로 차단합니다. 경고 무시 옵션을 관행적으로 쓰지 말고 영향, 완화 조치, 승인자를 기록합니다. 준비 완료 상태도 시간이 지나면 만료되어 설치 전에 검사가 다시 실행될 수 있습니다.

### 알려진 문제와 보안 정책의 충돌을 먼저 제거합니다

2606 알려진 문제에는 특정 Windows Defender 공격 표면 감소 규칙이 차단 상태일 때 solution update가 실패하는 조건이 포함됩니다. 이를 이유로 보안 정책을 영구 완화하지 않습니다. 공식 완화 절차, 적용 시간, 원복 확인과 보안 담당자 승인을 변경 계획에 포함합니다.

### 재시도보다 실패 증거를 보존합니다

Microsoft는 일부 노드가 실패한 경우 업데이트를 무작정 다시 실행하지 말고 Update history와 노드 로그를 확인하도록 안내합니다. 단계, 노드, 오류, 유지보수 모드, 워크로드 상태를 보존한 뒤 지원 문서나 지원 절차에 따라 다음 행동을 결정합니다.

## 실무 체크리스트

1. 모든 노드의 solution version, OS build, firmware, driver와 SBE 버전을 수집합니다.
2. 공식 release information에서 현재 버전의 지원 상태와 목표 업데이트 경로를 확인합니다.
3. 목표 릴리스의 known issues와 필요한 완화 조치를 변경 요청서에 연결합니다.
4. OEM 이미지·driver·SBE 추가 콘텐츠의 필요 여부와 확보 책임자를 확인합니다.
5. 준비 전 클러스터 상태, 저장소, 네트워크, Arc 연결과 워크로드 여유 용량을 점검합니다.
6. 가능하면 운영 구성을 닮은 테스트 클러스터에서 동일 경로를 먼저 실행합니다.
7. PrepareOnly 또는 포털 readiness check 결과에서 Critical·Warning 항목을 해소합니다.
8. 노드별 워크로드 이동, 일시 중지, 복구와 사용자 공지 기준을 정합니다.
9. UpdateRun, Update history와 필요한 이벤트 로그의 보존 위치를 정합니다.
10. 실패 단계별 중단, 원복 가능 범위, 지원 요청과 재시도 승인자를 지정합니다.

## BLRO 적용 범위

관련 서비스는 HCI와 프라이빗 클라우드, HCI 도입 준비도 체크리스트입니다.

- 진단 범위: 현재 버전, 노드·클러스터 상태, OEM 의존성, 업데이트 경로, 워크로드 여유와 변경 절차를 현황화합니다.
- 의사결정 산출물: 목표 경로, 사전 조치, 상태 검사 판정, 변경 창, 실패 대응을 담은 업데이트 준비 판단표를 만듭니다.
- 운영 검증: 준비 단계와 테스트 환경 결과, 로그 수집, 워크로드 이동·복구 절차를 확인합니다. 무중단, 호환성, 완료 시간 또는 성능은 사전 보장하지 않습니다.

## 제외 범위

- 특정 HCI·서버·OEM 제품의 우열, 가격, 성능 또는 절감률 비교
- 고객별 하드웨어·driver·firmware 호환성의 공개 확정
- 공식 지원 경로 밖의 개별 구성 요소 업데이트 또는 비공식 우회 절차
- 보안 정책의 영구 완화와 고객 환경의 비공개 구성·장애 이력 공개
