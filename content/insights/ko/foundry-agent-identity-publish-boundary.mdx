## 한눈에 보기

Foundry Agent Service는 2026년 3월 일반 공급이며, 에이전트가 도구를 호출할 때 쓰는 신원을 사람이 아니라 디렉터리 개체로 둡니다. 미게시 에이전트는 프로젝트 공유 신원을 쓰고, 게시하면 고유 신원이 새로 생깁니다.

- 결정: 에이전트가 자신으로 호출할지, 사용자 위임으로 호출할지, 게시 후 권한을 다시 줄지
- 전제: Agents service와 Evaluations는 Entra ID가 필요하고 API 키를 받지 않는다고 인증 문서가 적는다
- 불일치: 같은 달 블로그는 MCP 인증에 키 기반을 포함하고, 신원 문서는 일부 도구만 에이전트 신원을 지원한다고 적는다
- 범위: 운영 거버넌스 프레임워크가 아니라 게시 경계와 도구 호출 주체

## 문제 상황

에이전트를 프로토타입으로 돌릴 때는 프로젝트 하나의 공유 신원으로 도구를 붙이기 쉽습니다. 그 상태로 게시하면 호출 주체, 감사 단위, 권한 범위가 바뀌는데도 기존 역할 할당을 그대로 둔 채 운영에 넣는 경우가 있습니다.

Microsoft Learn 에이전트 신원 문서는 첫 에이전트를 만들 때 기본 블루프린트와 기본 에이전트 신원을 프로비저닝하고, 미게시 에이전트는 프로젝트 공유 신원으로 도구를 인증한다고 적습니다. 게시하면 전용 블루프린트와 전용 신원이 생기고, 공유 신원에 준 역할은 넘어가지 않으므로 다시 할당해야 합니다.

인증·권한 문서는 Agents service와 Evaluations에 API 키를 쓸 수 없고 Entra ID를 쓰라고 적습니다. 반면 Foundry 블로그의 MCP 인증 안내는 키 기반, Entra Agent Identity, 프로젝트 관리 ID, OAuth Identity Passthrough를 한 서비스에서 고른다고 적습니다. 신원 문서는 MCP와 A2A만 에이전트 신원 인증을 지원하고, 다른 도구는 키 또는 패스스루를 쓸 수 있다고 남깁니다. 운영 승인은 한 페이지의 인증 표만 인용하지 말고, 어떤 도구가 어떤 주체를 쓰는지 같은 기록에 남겨야 합니다.

## 지금 결정할 것

- 대상 과제가 미게시 실험인지, 게시 후 운영 호출인지
- 도구 호출이 에이전트 자신의 권한인지, 로그인한 사용자 위임인지
- 게시 후 새로 생긴 에이전트 신원에 어떤 자원 역할을 다시 줄지
- MCP 연결을 에이전트 신원, 프로젝트 관리 ID, 사용자 패스스루, 키 중 무엇으로 둘지
- 추론·평가 트래픽과 도구 트래픽을 어떤 네트워크 경계에 둘지

## 의사결정 기준

### 미게시 공유 신원과 게시 후 고유 신원을 같은 주체로 보지 않습니다

미게시 에이전트는 프로젝트 안에서 같은 신원을 공유합니다. 게시하면 에이전트 애플리케이션에 묶인 고유 신원이 생기고, 도구 호출 주체가 바뀝니다. 통합 시험이나 운영 소비, 감사 분리가 필요하면 게시 전 권한 재할당 목록을 만듭니다. 공유 신원에 넓게 준 역할을 운영 기본값으로 두지 않습니다.

### 참석 호출과 비참석 호출을 먼저 가릅니다

신원 문서는 사용자가 동의한 범위만 쓰는 참석 흐름과, 에이전트 자신의 역할 할당만 쓰는 비참석 흐름을 나눕니다. 개인 사서함이나 사용자 단위 SaaS는 패스스루를 검토하고, 공유 저장소나 시스템 작업은 에이전트 신원을 검토합니다. 두 흐름을 한 연결에 섞지 않습니다.

### Agents service 인증과 MCP 도구 인증을 한 표로 합치지 않습니다

인증 문서는 Agents service에 API 키를 허용하지 않습니다. 블로그는 MCP에 키 기반을 포함합니다. 신원 문서는 에이전트 신원을 지원하는 도구가 제한적이라고 적습니다. 런타임 호출 인증과 도구 연결 인증을 분리해 적고, 키가 남는 연결은 평가용인지 운영용인지 표시합니다.

### 데이터 경계는 추론만이 아니라 도구 경로까지 봅니다

3월 GA 안내는 고객 가상 네트워크, 공용 송신 없음, MCP와 Azure AI Search, Fabric 데이터 에이전트까지 사설 경로를 연장한다고 적습니다. 호스티드 에이전트와 Voice Live는 미리보기로 남아 있습니다. 일반 공급 런타임과 미리보기 호스팅을 같은 운영 승인으로 묶지 않습니다.

## 실무 체크리스트

1. 과제별로 미게시 실험, 게시 예정, 이미 게시됨을 나눕니다.
2. 도구마다 호출 주체가 에이전트 자신인지 사용자 위임인지 적습니다.
3. 프로젝트 JSON의 공유 신원과 게시 후 고유 신원을 구분해 기록합니다.
4. 게시 후 저장소, 검색, 논리 앱 등 하류 자원 역할을 새 신원에 다시 할당합니다.
5. MCP 연결의 인증 방식을 에이전트 신원, 관리 ID, 패스스루, 키로 표시합니다.
6. Agents service와 Evaluations에 키를 쓰지 않는다는 인증 문서를 변경 요청서에 붙입니다.
7. 사설 네트워크가 필요하면 모델 호출과 도구 호출을 같은 경계로 볼지 적습니다.
8. 호스티드 에이전트나 Voice Live를 쓸 경우 미리보기 조건을 운영 범위에서 뺍니다.

## 제외 범위

- 특정 모델, 오케스트레이션 프레임워크, 에이전트 제품의 우열이나 성능 비교
- 고객별 규제 적용, 라이선스 구매, 계약 해석의 확정 판정
- 호스티드 에이전트 미리보기를 일반 공급처럼 쓰는 가정
- 오류 방지, 보안, 규제 적합성, 운영 결과의 사전 보장
- 기존 AI 운영 거버넌스 의사결정 흐름 글을 다시 쓰는 범위

## 이 이슈를 BLRO가 다루는 방식

- 진단 범위: 미게시와 게시 신원, 도구별 호출 주체, 역할 재할당, 네트워크 경계를 현황화합니다.
- 의사결정 산출물: 과제별 신원 선택, 게시 전 권한 목록, MCP 인증 방식, 문서 불일치 기록을 담은 판단표를 만듭니다.
- 운영 검증: 게시 전후 토큰 주체와 도구 호출 실패 지점을 시나리오로 확인합니다. 특정 모델 품질, 규제 적합성, 위험 제거를 사전 보장하지 않습니다.
