ZTNA와 SSL VPN은 제품 이름만으로 선택할 수 없습니다. 핵심은 “누가, 어떤 장치에서, 어떤 애플리케이션에, 어떤 조건으로 접근해야 하는가”입니다. **네트워크에 들어온 뒤 무엇이 가능한가**가 아니라, 요청한 리소스에 필요한 권한만 어떻게 검증할지부터 정리해야 합니다.

## 먼저 그릴 접근 경로 5가지

| 경로 | 확인할 질문 | 설계 입력 |
| --- | --- | --- |
| 사용자 | 임직원·협력사·관리자의 목적은 다른가 | 역할과 승인자 |
| 장치 | 관리 장치와 비관리 장치를 구분하는가 | 장치 상태·예외 |
| 애플리케이션 | 전체 네트워크가 필요한가, 특정 앱이면 충분한가 | 접근 단위 |
| 세션 | 재인증·권한 상승·종료는 언제 필요한가 | 세션 정책 |
| 운영 | 장애·예외·계정 회수는 누가 처리하는가 | 운영 절차와 로그 |

## 비교의 출발점

NIST의 Zero Trust Architecture는 네트워크 위치나 자산 소유만으로 암묵적 신뢰를 부여하지 않고, 리소스 접근 전에 사용자와 장치의 인증·인가를 별도 기능으로 다룰 것을 설명합니다. 따라서 “ZTNA가 VPN을 대체하는가”보다 **업무별 접근 단위와 기존 애플리케이션 제약이 무엇인가**를 먼저 확인하는 편이 안전합니다. [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final)

## 단계적 전환 순서

1. 원격접속 사용자를 업무 목적과 민감도로 나눕니다.
2. 애플리케이션별 프로토콜, 네트워크 의존성, 인증 연동, 운영시간을 기록합니다.
3. 특정 사용자군과 애플리케이션으로 정책·로그·장애 대응을 검증합니다.
4. 예외 접근에는 종료일, 승인자, 재검토 기준을 둡니다.
5. 전체 전환 전에는 계정 회수와 긴급 접근 절차까지 리허설합니다.

## 흔한 오류와 보류 조건

모든 원격업무를 한 번에 바꾸거나, 장치 상태·계정 수명·레거시 프로토콜을 나중에 검토하면 예외가 운영 표준이 되기 쉽습니다. 애플리케이션 단위 접근이 가능한지, 사용자 지원 체계가 있는지, 비상 시 우회 절차가 있는지 확인되지 않은 업무는 전환 대상이 아니라 검증 대상입니다.

## 이 글의 산출물

결과물은 제품 비교표가 아니라 **접근 흐름 지도, 사용자·장치·앱별 정책 표, 예외 관리대장, 단계별 검증 시나리오**입니다. 이 자료를 바탕으로 네트워크 보안 진단 범위를 정하면 현재 VPN을 유지할 영역과 먼저 검증할 영역을 분리할 수 있습니다.

## 비교 항목

- 네트워크 전체 또는 애플리케이션 단위 중 필요한 접근 범위
- 사용자와 장치 신뢰를 확인하는 방식
- 레거시 애플리케이션과 프로토콜 지원 조건
- 정책 변경, 장애 대응과 사용자 지원 절차
- 기존 인증·보안 체계와의 연계 범위

단계적 전환이 필요한 경우 사용자군과 애플리케이션을 나눠 검증하고, 예외 접근의 종료 조건을 함께 정합니다.
